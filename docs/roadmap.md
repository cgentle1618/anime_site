# Roadmap

Last verified: 2026-09-12 (the admin account holds no user data; the authorization redesign is complete: phases 0, A, A.1, B, C and D)

## What this is for

This file replaces `roadmap.md`. It is the one place that answers three questions: what has already shipped (so nobody re-plans it), what is being worked on right now, and what was consciously left undone. The "Done" log is one line per feature, newest first, distilled from the git history and the retired plan. "Next" is empty on purpose until a piece of work is picked up. "Deferred / known debt" lists things the code still does the awkward way; each line was checked against the source on the verification date, so if a line is stale the code moved and the line should go.

The rule from `CLAUDE.md` still applies: when implementing from this file, pause and ask for permission after each step or set of steps, record progress in the "Next" section only, and do not rewrite the plan itself.

| 2026-09-12 | **Two field groups deleted, and nothing replaced them**: `credits` and `system_info` left `FIELD_GROUPS`, which is down to the three that are genuinely object-scoped. **`credits` was never worth gating** - studio, director and the rest are what an entry *is*. **`system_info` turned out to be two timestamps nothing displays**: `created_at`/`updated_at` say when the catalogue ROW was last edited, a fact about the database rather than about the work, and the only page that showed one was a "Last updated" figure on four detail pages, now removed. The group also named the entry id printed down a poster spine, which was **never actually gated** - `system_id` is the page's own URL - so that decoration is drawn on `is_superuser`, deliberately not on `super`, and needs no permission at all. **The interesting part is the route not taken.** This began as "bind system info to roles, super and admin only", was built that way - a `view` permission family, a lock table row, a second axis inside `gated_columns` reversing Phase B - and was then unwound, because the question "what is system_info actually?" was asked after the design and not before it. The answer made the whole structure unnecessary: nothing displays the timestamps, so there is nothing to withhold. **The reversal also retracted a defect report**: the claim that a role-axis permission would be invisible to a superuser in the SPA was wrong - `AuthContext`'s `has()` already short-circuits on `isSuperuser`, mirroring the server, and only the server half had been read. | 2026-09-12 | **A logged-out visitor gets `safe`, and that is not a setting**: which mode an anonymous request resolved to was an administrator's choice, stored as `access_mode.is_guest_default` behind a partial unique index and offered on `/access-modes` as a radio repeated under every mode row. Both halves are gone. `resolve_mode` looks up `MODE_SAFE` **by key**, the column and its index are dropped (`p2g3guestsafe`), and the page offers no control at all - `safe`'s own description carries the fact. **The flag was a defence in a scenario that never occurred, charging for it in the one that does.** The redesign spec had explicitly rejected resolving the literal key, on the grounds that editing the mode you sit in yourself would then republish it to the internet - true, and equally true of the flag, because the seeder flags `safe` and nobody ever moved it. What the flag did buy was a column an admin can edit, which is a column a **Pull All, a migration or a hand-edit can move to `unrestricted`** - publishing every labelled entry to the anonymous internet while looking like a successful restore, with nothing on any screen reporting it. The spec's reasoning is corrected in place rather than quietly superseded. **The live risk is unchanged and is stated rather than designed around**: widening `safe` widens what the internet sees, immediately, exactly as before. Checked and deliberately **not** changed: a logged-out visitor already got no mode switcher rather than a disabled one - `held_modes()` returns `[]` without an account and the switcher renders `null` below two modes - so other modes were never advertised to anonymous visitors and no chrome work was needed |
| 2026-09-12 | **Locked grants on the role editor**: every cell of the permission grid was an administrator's free choice, including the ones that are not a choice at all - `admin.authz` could be handed to any role through the very page that permission governs, and `super` could be quietly stripped of the catalogue that defines it. `permissions.locked_permissions(role_name, is_superuser)` now returns `(locked_on, locked_off)` per role: **`admin.authz` is grantable to nothing** (the superuser short-circuit is the only way to hold it), `super` holds everything but it and can change none of it, `guest` is view-only - no `manage.*` and, new here, **no `self.*`**, because every anonymous request resolves to that role and a list it owned would be one list shared by the whole internet - and `user` and every custom role may take `manage.catalog` but never `manage.pipelines`, since one Pull All overwrites every table, accounts and role assignments included. **One table, three readers**, because a UI-only lock is a suggestion: `RoleResponse` serves the two sets so the editor draws those boxes disabled, both write routes answer **409** on a payload that disagrees, and `ensure_rbac_seed` reconciles the stored grants on start - adding a missing locked-on grant, dropping a locked-off one. That last reader **inverts the seed's own top-up-only-an-empty-role rule**, and deliberately: that rule exists so a deliberate removal sticks, and a locked grant was never anyone's to remove, so its test was flipped rather than worked around. The one cell that does not follow the pattern is the one worth reading twice - **a superuser's `self.*` is locked OFF**, since `Viewer.has()` does not short-circuit that family, so drawing the admin's Own Rows ticked would have stated the opposite of what the resolver does. What was deliberately **not** done: no reason text on a disabled box, and the `super`/`admin` grids render fully rather than collapsing to a banner - the vocabulary stays visible on every role, so the page still teaches what exists |
| 2026-09-12 | **The Unrestricted mode carries every label, derived rather than stored**: creating a content label granted it to no access mode, so the first entry tagged with it vanished from **every session in the installation, the owner's included** - and since a hidden entry deliberately 404s to stay indistinguishable from a missing one, the entry read as *deleted*: the detail page 404'd, the edit 404'd, and the row was sitting untouched in the database and in the sheet the whole time. That was the documented, deliberate behaviour - fail-closed, with `/access-modes` as the place to grant the new label - and the fail-closed reasoning was right about every mode except the one whose entire meaning is "no restrictions". A mode called **Unrestricted**, described as "Every entry and every field. The widest mode", that a label minted today silently narrows, is not a safe default; it is an entry that disappeared. So `unrestricted`'s sets are **derived**: `cache.mode_sets()` returns every `content_label` row and every `FIELD_GROUP_KEYS` entry for it, whatever the tables hold. Derived at the **one chokepoint all three resolution paths share**, rather than kept in step by the write paths, because the write paths are not the only way rows arrive - a Pull All, a migration or a hand-edit would each have to remember. `PUT /grants` answers **409** for it and the SPA draws its boxes disabled with no Save, both halves, since a UI-only lock is a suggestion; label creation also writes the row, so the tables and the derivation agree for anything reading them. **The second consequence was worse than the first and nobody would have connected it**: `require_unscoped_mode` compares the session's mode against every label that exists, so minting a label also locked **Backup and Pull All** out with a 401 for the whole installation until somebody granted it. Two tests in `test_pipeline_mode_gate.py` were asserting exactly that narrowing *through* `unrestricted`; the rule they protect is still real, so they moved onto a custom row-set mode and a mirror test now pins that `unrestricted` does not narrow. What was deliberately **not** done: `borderline` still only carries what it was granted, and a per-account denial still subtracts from `unrestricted` - both are an admin's explicit act, and neither is drift |
| 2026-09-12 | **Saved usernames on the login page**: swapping between the accounts that share a machine meant retyping a username, because signing in as somebody else is sign out then sign in - there is no in-place switch and there should not be one. The form keeps up to three usernames in that browser's `localStorage` (`frontend/src/lib/savedUsers.js`) and fills itself from a click. **Usernames only** - no password, no token, nothing that authenticates, and the buttons say "Use" rather than "Sign in as" so the control does not promise more than it does. A name is saved only on a sign-in that **succeeded**, so a typo never spends a slot, and the cap does **not** evict: a fourth name is simply not remembered, because silently dropping a name somebody kept, to make room for a one-off login, is noticed only when the name you wanted is gone. Every read and write is inside a `try`/`catch`, so a private window or blocked site data degrades to "no saved users" rather than a blank form. The page's wording went with it: the slip was tabbed "Admin" and headed "Admin access" when the form was an admin door, and the header said the same thing four times over, so it is one heading, "Sign in", and the placeholder is `user123` rather than the real seeded `admin` |

| 2026-09-12 | **Clean orphaned data - the reviewed diff-and-delete**: Pull is upsert-only, so an entry deleted on one machine survived every Pull All on the other, forever, and the two databases silently diverged. `GET /api/data-control/clean/scan` diffs thirteen tabs against the sheet and reports every local row it no longer mentions; `POST /clean/apply` deletes the ones an admin ticks. There is deliberately **no freshness gate**: in the workflow that creates the garbage the sheet is *ahead* of the database - the machine that performed the deletion is the one that wrote it - so "back up first" would rewrite the garbage into the sheet and destroy the only evidence the diff has. **Apply re-scans** and deletes only ids still judged orphaned, because the question is never "did the delete run" but "is what got deleted still the set that was reviewed". A Sheets outage or a tab with fewer than two rows aborts the whole run rather than one tab, because Pull's continue-and-report policy is right for an upsert and catastrophic for a delete |
| 2026-09-11 -> 09-12 | **The authorization redesign** (phases 0, A, A.1, B, C and D): `admin` was one permission guarding 89 route dependencies across 27 routers, held by a role that is `is_superuser` and therefore holds everything implicitly - so there was no way to let a second person manage the catalogue without also handing them the ability to rewrite who may do what. It became **two disjoint axes**. The **role** answers *what kinds of operation may this account perform* - `admin.authz` (roles, users, labels), `manage.catalog` (entry CRUD and the catalogue), `manage.pipelines` (Backup, Pull, Fill, Replace, Calculate), plus `media_type.*` and the `self.*` family - with a `super` role holding both `manage.*` and not `admin.authz`, deliberately **not** `is_superuser`, because the point of the role is that its grant set is finite and inspectable. The **access mode** answers *which objects can those operations reach in this session*: content labels and field groups left the role axis for five new tables, and `label_perm()` / `field_group_perm()` were **deleted** so no code can ask the role axis an object question - a stale call would have answered `True` for a superuser, and an ImportError that stops the build beats a behaviour that quietly changes. Four defects worth keeping: the seeded `safe` mode had to be **derived** from what the guest role actually holds rather than from the spec's stated default, which would have published other people's personal reviews to every logged-out visitor; `users.py`'s "you cannot delete yourself" guard had silently stopped firing when the dependency's return type changed from `dict` to `Viewer`; the SPA's **nav is a second, independent permission surface** from `App.jsx`'s routes and was left gating on a deleted permission; and the per-account panel shipped **unmounted** - written, styled, reviewed and rendering nothing, with eslint saying so three times as a *warning*, so `npm run lint` exited 0. Specs and plans under `docs/superpowers/`; the gates themselves are described in [authorization.md](authorization.md) |
| 2026-09-09 -> 09-10 | **Multi-user, Steps 0-5**: the data model stopped assuming one person. **Step 0** gave every entry a row in a `media` supertable keyed by the same `system_id` the detail row already had, so anything pointing at "some entry" uses a real foreign key instead of an ambiguous `(media_type, entry_id)` pair; six link tables moved onto it and the database took over the cleanup. ## Next

**The authorization redesign**, at the brainstorm stage as of 2026-09-10.
`docs/authorization.md` was audited against the code before starting - ten
stale claims, every one of them a rule a later step had narrowed rather than
removed - and now ends with a **Known drift** section naming the three
half-finished pieces the redesign has to settle: the `personal_notes` field
group, which governs one query parameter and nothing else; the absence of any
SPA surface for a non-admin account, which makes the `user` role usable but not
useful; and one remark per owner, site-wide. Progress is tracked in
`docs/PROGRESS.md`.

Step 5 of the multi-user programme - the last of it - shipped on 2026-09-10,
and the auth-hardening gate it left behind closed the same day.

**Another person can now be given an account.** Two auth items stay open by
choice and neither blocks that: session lifetime is a flat 24 hours with no
refresh or revocation, and there is no password reset (an admin sets one at
`/users`).

The guest-fallback removal landed the same day, so the only other thing left is
**self-hosting**, which remains the intended production step and is still not
built (`docs/deployment-selfhost.md`): its blocking code change, the production
signal, is done, and what remains is the box, the compose file, the domain and
tunnel, and backups. Until that lands, local development is the only runtime.

## Deferred / known debt

**Left by Step 5, for the authorization redesign:**

- **One remark per owner, site-wide.** `remark` is a personal-scope section,
  but its read path is a class-level `column_property` that cannot know who is
  asking, so `ix_note_one_remark_per_owner` stays per-owner and a second user's
  remark is refused by the database rather than shown to the first user.
  Recorded in `app/models/__init__.py` and pinned by
  `tests/api/test_remark_author.py`.
- **The notes page has no UI for a non-admin.** A `user`-role account may write
  its own personal notes through the API and cannot reach them in the SPA.
- **`field_group.personal_notes` is only half rebuilt.** It governs
  `GET /api/notes?author=` and nothing else; `docs/authorization.md` says so.
- **Quotes and memes stay universal by design** - shared, unfiltered, no
  per-user copies. Their `author_id` is provenance only.

**Left by Step 4, and closed by Step 5:**

- **A password does not travel, by design.** An account Pull creates on the
  arriving machine carries `UNUSABLE_PASSWORD_HASH` and cannot be logged into
  until an admin sets one at `/users`. Bounded and one-off per user per
  machine; the tradeoff and its reasoning are in
  [data-actions.md](data-actions.md#2-sheet-tab-registry-tabspy) and
  [authentication.md](authentication.md).
- ~~**`note`, `meme` and `quote` are still not per-user.**~~ Closed by Step 5:
  all three carry an `author_id`, which travels as a raw uuid because the
  `Users` tab makes ids agree across machines. The Note and Meme tabs also lost
  `owner_type` / `owner_id` and gained the four owner columns; an older sheet
  still Pulls through the legacy fallback in `pull.py`.

**Left by Step 2, for Steps 4-5:**

- ~~**The `acting_user_id` guest-to-admin fallback still stands.**~~ Closed on
  2026-09-10, and the honest replacement this line predicted is what shipped:
  a guest has no list at all. `installation_owner_id` keeps the restore and
  pipeline half under its own name.
- ~~**`self.personal_notes` is granted but enforced nowhere.**~~ Closed by
  Step 5: it gates every personal-scope note write in `app/routers/note.py`.

**Left by Step 1, for Steps 3-5:**
