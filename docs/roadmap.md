# Roadmap

Last verified: 2026-09-10 (Step 2, accounts and profiles)

## What this is for

This file replaces `roadmap.md`. It is the one place that answers three questions: what has already shipped (so nobody re-plans it), what is being worked on right now, and what was consciously left undone. The "Done" log is one line per feature, newest first, distilled from the git history and the retired plan. "Next" is empty on purpose until a piece of work is picked up. "Deferred / known debt" lists things the code still does the awkward way; each line was checked against the source on the verification date, so if a line is stale the code moved and the line should go.

The rule from `CLAUDE.md` still applies: when implementing from this file, pause and ask for permission after each step or set of steps, record progress in the "Next" section only, and do not rewrite the plan itself.

| 2026-09-10 | **Accounts, the `user` role, profiles and community aggregates (multi-user Step 2)**: the data model became multi-user in Steps 0 and 1; this is the step that lets a second person use it. **One new permission family**: `self.list` and `self.personal_notes` join `admin`, `media_type.*`, `field_group.*` and `label.*`. Every other family answers "may you *see* this"; `self` answers "may you *write your own*", and it is the only family whose keys are constants rather than derived, because each names a router dependency. Served from `/api/roles/catalog`, so the role editor rendered the new family **with no frontend change at all** - the payoff for serving the catalogue instead of mirroring it. **One new role**: `user`, `sort_order` 50, system, not superuser, holding `default_guest_permissions()` plus the two `self.*` grants and nothing else - derived from guest rather than restated, so a media type added later reaches both roles at once. Catalogue writes stay behind `Depends(get_current_admin)`, so **no new admin surface appeared**, and the existing `/users` page could create an account on the new role without being touched: its role `<select>` is populated from `GET /api/roles/`. **One boolean**: `users.list_is_public`, NOT NULL, default false - private by default, written only by its owner through `PATCH /api/account/settings`, and deliberately absent from `ManagedUserUpdate` because whose list is visible is the account holder's decision and not the inviter's. **Four routes and their pages**: `/api/account/settings` (the toggle), `/api/profile/{username}` (one person's list, all nine types in one query - the payoff for the `media` supertable), `/api/community/{media_id}` (what the public lists think of one work), and `/api/me/list/{media_id}`, which the plan assumed Step 1 had shipped and which did not exist: Step 1 left every list write inside the per-type admin entry endpoints, so `self.list` named no code and would have been the inert grant `permissions.py` exists to forbid. **A private list answers 404, not 403**, to everyone but its owner and an admin, so a stranger cannot enumerate accounts; a public list is filtered by the **reader's** media-type and content-label permissions, never the owner's, through a new `apply_media_visibility` that expresses `apply_entry_visibility`'s two gates over `media`; and the profile's status counts are tallied from the filtered rows rather than by a second `GROUP BY`, or a hidden entry would leak as a discrepancy in the totals. **Community figures count public lists only** - a correctness rule, not a courtesy: a total that moved when a private list changed would let anyone read a private list one bit at a time. The sample size is always printed beside the average because "A" over two ratings is not the claim "A" over two hundred is. **The spec's two SQL sketches were both wrong** and are corrected in one module: `my_rating` is a letter grade stored as a String, so `ORDER BY my_rating DESC` puts `A+` before `A` and `AVG(my_rating::numeric)` raises on the first row; `app/services/domain/rating_points.py` maps S=8 down to F=1 and both the profile ordering and the community average go through it. Two migrations, `m2a1users` (raw SQL, copying *this installation's* guest grants rather than recomputing them) and `m2a2public`. **Two things this step deliberately did not do**, both still open: the `acting_user_id` guest-to-admin fallback still stands, so a logged-out visitor still reads the lowest-username admin's list on the public pages; and `self.personal_notes` is granted but enforced nowhere, because note scoping is Step 5. **Gated**: the cookie's unconditional `secure=False` and the missing `JWT_SECRET_KEY` / `ADMIN_PASSWORD` fail-fast are untouched by design and must land before any account is created for another person - `docs/authentication.md`. ## Next

Nothing in progress. Step 2 of the multi-user programme shipped on 2026-09-10.

**Before another person gets an account, the auth-hardening project has to
land**: the login cookie is `secure=False` unconditionally and nothing fails
fast on a default `JWT_SECRET_KEY` or `ADMIN_PASSWORD`. Step 2 was implemented
without them by design and must not be *used* without them - see
`docs/authentication.md`. That is the natural next piece of work.

After it, either Step 3 of the multi-user programme (per-user planning and the
`seasonal` counters) or the guest-fallback removal below. **Self-hosting remains
the intended production step** and none of it is built yet
(`docs/deployment-selfhost.md`); until it is, local development is the only
runtime.

**Left by Step 2, for Steps 3-5:**

- **The `acting_user_id` guest-to-admin fallback still stands.** An
  unauthenticated viewer still resolves to the lowest-username admin, so the
  public pages still show that account's statuses, ratings and progress. Step
  2's plan neither removes it nor lists it in its Definition of done - the step
  built the accounts a real answer *needs* (a `user` role, per-user visibility,
  a profile page) and left the question of what a logged-out visitor should see
  open. Removing it is a visible behaviour change: the honest replacement is
  probably "a guest has no list at all", which blanks the personal columns on
  every public page. `app/services/domain/user_list.py`.

  personal notes are still gated only by the `personal_notes` field group. Note
  scoping is Step 5. The permission exists now because the role that holds it is
  seeded now.
