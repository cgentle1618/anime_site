# Roadmap

Last verified: 2026-09-10 (Step 5, notes scoped per section)

## What this is for

This file replaces `roadmap.md`. It is the one place that answers three questions: what has already shipped (so nobody re-plans it), what is being worked on right now, and what was consciously left undone. The "Done" log is one line per feature, newest first, distilled from the git history and the retired plan. "Next" is empty on purpose until a piece of work is picked up. "Deferred / known debt" lists things the code still does the awkward way; each line was checked against the source on the verification date, so if a line is stale the code moved and the line should go.

The rule from `CLAUDE.md` still applies: when implementing from this file, pause and ask for permission after each step or set of steps, record progress in the "Next" section only, and do not rewrite the plan itself.

| 2026-09-10 | **Notes scoped per section (multi-user Step 5)**: every one of the 29 `NOTE_SECTIONS` entries now declares a **`scope`** - 20 `catalog` (one shared set of rows, admin-authored, read by everyone), 7 `personal` (one set per user, read only by its author), and `None` for the two `SHAPE_EXTERNAL` sections, `quotes` and `memes`, which store no `note` row. `NoteSection.scope` has **no default and is declared before the first defaulted field**, so the dataclass itself refuses an entry that forgets it: a default would let the next section added inherit one by omission, and the wrong inheritance publishes one person's private note to every user. The distinction lives in the registry rather than the schema because that module's own rule is *adding a section is one entry and no migration*, and a reclassification must obey it - a registry edit plus a data reassignment, never an `ALTER TABLE`. **Provenance before filtering**, which is the whole safety property: `note`, `quote` and `meme` each got a `NOT NULL author_id` referencing `users(id) ON DELETE CASCADE`, backfilled to the admin, in three migrations that changed no read at all, and only then did anything start filtering on it - so a half-applied plan can never hide a note that used to be visible. The author is **who is asking**, never the payload: the create routes pop any `author_id` out and take `viewer.user_id`, and the column is on the response schemas and not on the create/update bases. **Enforcement**: `GET /api/notes` returns a viewer's own personal rows and nobody else's, a logged-out visitor gets none at all, and catalogue rows fall through untouched - two viewers, one entry, two different personal answers and one identical catalogue answer. Writes read the scope from the registry, so reclassifying a section changes who may write it with no change to the router. The permission is Step 2's **`self.personal_notes`**, not the plan's proposed new `note.write_own`: the two name one idea and that grant's own catalogue description is this rule verbatim, so Step 5 enforces what Step 2 seeded rather than minting a second name for it - which closes the *granted but enforced nowhere* debt Step 2 recorded. **`field_group.personal_notes` changed job**: it is applied only to rows the viewer did *not* author (hiding someone's own notes from them is not a permission, it is a bug), and what it now governs is `GET /api/notes?author=<username>`, honoured only when that user's `list_is_public` **and** the viewer holds the group - an unknown user, a private list and a missing group all answer the same 403, so the reply cannot be read as *this account exists*. **`note` and `meme` swapped their FK-less `(owner_type, owner_id)` pair for four nullable foreign keys** - `media_id`, `collection_id`, `franchise_id`, `series_id` - with `num_nonnulls(...) = 1` (`ck_note_one_owner`, `ck_meme_one_owner`), because an owner that may be a grouping tier cannot be one FK: `media.system_id` cannot hold a franchise id. Every owner cascades now, with no service code involved, and the old pair survives as **read-only Python properties** derived from whichever column is set - which is what kept the whole API shape, `drop_hidden_rows`, `entry_ref_for` and the SPA unchanged, and, being properties rather than columns, keeps them out of the Google Sheets row. `note`'s two indexes were rebuilt on the four columns with **NULLS NOT DISTINCT**, without which three always-NULL columns would let every owner hold unlimited remarks. Pull learned the same lesson Step 3 taught it - the header filter drops any parsed key the sheet header did not carry, which ate the translated owner columns - so the Note and Meme tabs put their legacy pair back explicitly and resolve it against `media` and the three tier tables; a row whose owner resolves to nothing is skipped and reported rather than written, and a blank `author_id` falls back to the admin. **Two limitations are carried forward deliberately**: one remark per owner *site-wide*, because the `remark` read path is a class-level `column_property` that cannot know who is asking, so a second user's remark is refused by the database rather than shown to the first user - the conservative failure, recorded in the code and pinned by tests; and quotes and memes stay **universal**, carrying an author for provenance while every viewer reads the same rows. **No frontend work**: `scope` reaches the API and nothing renders it, so a `user`-role account can write personal notes through the API but not through the UI. That, and the wider authorization redesign, stay deferred. Five migrations, `m5a1notescope` -> `m5a2quoteauthor` -> `m5a3memeauthor` -> `m5b1notefks` -> `m5b2memefks`.
